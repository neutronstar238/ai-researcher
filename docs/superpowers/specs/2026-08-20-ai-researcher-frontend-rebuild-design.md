# AI-Researcher 前端整体重建设计

- 日期：2026-08-20
- 状态：用户已确认方向，等待书面设计复核
- 基准视觉：用户提供的“研启智链 / AI-Researcher - 研究指挥中心”桌面截图
- 基准视口：1440 × 900，浏览器缩放 100%
- 实施边界：整体替换现有前端；保留 Python 科研引擎、研究数据和现有 HTTP API

## 1. 背景与问题

仓库当前默认前端是原生 HTML、CSS 和 JavaScript 编写的“科研计划台”。它能调用真实 API，但页面结构以题目输入、运行列表和单次运行详情为中心，与目标截图所表达的“研究指挥中心”信息架构不一致。仓库中的 `web/legacy-dashboard/` 虽然在视觉上更接近截图，但其卡片数据和导航主要是静态展示，不能作为交付基础。

本次工作不在旧页面上继续修补，而是完整重建前端。新前端以截图中的研究总览为首页，保留现有真实运行能力，并把研究任务、阶段、产物、批量任务和技能候选组织为一套一致的应用壳层。

## 2. 目标

1. 在 1440 × 900 下重建截图的整体层级、信息顺序、比例、颜色、留白和状态表达。
2. 将现有可用 API 映射到新界面，所有主要按钮产生真实请求、路由或状态变化。
3. 用统一导航承载研究总览、项目、文献、实验、数据、知识、写作、复盘、智能体、审批和设置入口。
4. 准确展示加载、空数据、服务错误、权限或能力缺失，不用硬编码业务数据伪装成功。
5. 保留现有科研流程的 fail-closed 行为；前端只展示和发起操作，不绕过科学门禁。
6. 提供可重复的构建、测试和浏览器视觉验收流程。

## 3. 非目标

1. 不重构研究循环、模型调用、文献检索、实验执行或论文生成逻辑。
2. 不在本任务中新增多用户认证、团队权限、数据库或云部署体系。
3. 不为现有后端没有暴露的知识图谱和审批能力制造前端假接口。
4. 不以静态演示数据替代生产状态；视觉 QA 如需固定数据，只使用测试夹具和隔离的测试服务。
5. 不在本任务中实现工程规格所描述的完整多租户平台后端。

## 4. 方案选择

### 4.1 采用方案：React + Vite + TypeScript

新建独立 `frontend/` 工程，使用 React、TypeScript 和 Vite。源代码按页面、组件、API、状态和领域映射拆分；生产构建输出到仓库现有 `web/` 静态根，由 `autoresearch.api.app` 继续托管。

选择原因：

- 页面已从单一控制台升级为多视图应用，组件化和类型约束能够显著降低后续维护成本。
- Vite 可生成固定名称的 `app.js` 和 `styles.css`，与当前静态服务契约兼容。
- React Router、查询缓存和测试工具能覆盖导航、请求、失效、弹窗和异步状态。
- 这一选择与仓库内已有平台工程规格的 React 方向一致，但不扩张到完整后端重构。

### 4.2 未采用方案：继续使用原生 HTML/CSS/JavaScript

优点是改动文件少、无需构建工具；缺点是多页面状态、异步请求、弹窗和数据映射会继续集中在大型脚本中，无法满足整体重做后的可维护性要求。

### 4.3 未采用方案：前后端全栈同时重建

该方案可以一次补齐审批、知识图谱、权限和完整聚合接口，但会把“前端整体重做”扩张为平台重构，风险、工期和验证面均明显增加，因此不属于本次任务。

## 5. 总体架构

```text
Browser
  -> React AppShell
       -> Router
       -> Query cache
       -> UI state store
       -> Domain adapters
            -> typed API client
                 -> existing aiohttp API
                      -> ResearchApiService
                      -> existing run and artifact storage
```

前端分为四层：

1. `app`：应用入口、路由、全局错误边界、查询客户端和主题。
2. `features`：dashboard、projects、runs、artifacts、batches、skills、settings 等领域功能。
3. `components`：AppShell、Sidebar、Header、卡片、表格、状态、弹窗、抽屉和反馈组件。
4. `lib`：API 客户端、领域映射、日期格式、状态标签和浏览器持久状态。

业务数据以服务端为准。前端只允许主题、侧栏折叠、选中运行和筛选条件进入浏览器本地存储。

`web/legacy-dashboard/` 不再被任何路由引用。是否物理删除该历史目录不影响运行；本任务默认保留它作为未服务的历史参考，避免不必要的数据删除。

## 7. 信息架构与路由

| 导航 | 路由 | 本次提供的真实能力 |
|---|---|---|
| 研究总览 | `/` | 生命周期、当前任务、近期研究、趋势、系统状态、创建任务 |
| 项目空间 | `/projects` | 运行列表、搜索、状态筛选、选择运行、创建研究 |
| 文献库 | `/literature` | 按运行展示文献相关产物和可下载文件 |
| 实验管理 | `/experiments` | 实验相关阶段、运行状态和实验产物 |
| 数据资产 | `/assets` | 统一产物列表、类型筛选、下载 |
| 知识图谱 | `/knowledge` | 准确说明当前 API 能力边界，并链接已有证据类产物 |
| 写作中心 | `/writing` | Markdown、TeX、PDF 和报告产物 |
| 复盘洞察 | `/reflections` | 失败信息、验证结果、恢复入口和进化状态 |
| 智能体中心 | `/agents` | Skill 候选、进化状态和发起进化 |
| 审批中心 | `/approvals` | 展示后端审批能力边界，不模拟批准或拒绝 |
| 系统设置 | `/settings` | 健康状态、服务信息、主题和显示偏好 |

桌面端使用浏览器历史路由；服务端为非 API 路径返回 SPA 入口。页面刷新不应产生 404。

## 8. 视觉系统

### 8.1 应用壳层

- 桌面左栏宽 `220px`，浅灰蓝背景，右边界 `1px`。
- 主区最大基准宽 `1220px`，页面背景为接近截图的冷白色。
- 顶部标题区显示页面标题、动态日期、通知、帮助和操作者菜单。
- 小于 `1280px` 时侧栏可折叠；小于 `1024px` 时使用抽屉式导航和单列卡片。

### 8.2 颜色与字体

- 主色：深蓝 `#0B3B82` 与交互蓝 `#165DFF`。
- 成功：`#13A88A`；警告：`#F59E0B`；失败：`#E11D48`。
- 正文：`#1F2A44`；次级文字：`#667085`；边框：`#DCE3ED`。
- 字体使用 Inter、Microsoft YaHei、PingFang SC 和系统无衬线回退。

### 8.3 图标和品牌

- 使用 `lucide-react`，因为仓库工程规格和截图中的线性图标语言均与之匹配。
- 不使用 emoji、文字字符或手绘内联 SVG 代替 UI 图标。
- 生成一份独立的圆形“研启智链”品牌图像，作为侧栏 Logo；生成资源需与截图的蓝、青、金配色一致。

### 8.4 研究总览布局

从上到下保持如下顺序：

1. 页面标题与日期。
2. 八阶段研究生命周期。
3. 两列卡片：当前研究任务、近期研究/本周选题。
4. 两列卡片：研究证据覆盖趋势、待处理操作或审批能力状态。
5. 系统健康状态条。

卡片使用白色背景、浅边框、轻阴影和 `10px–12px` 圆角。视觉对齐优先保证信息顺序、列比例、行高和留白，不复制截图中的静态业务数值。

## 9. 数据映射

### 9.1 API 清单

新前端只依赖当前已存在的接口：

- `GET /api/health`
- `GET /api/runs`
- `POST /api/runs`
- `GET /api/runs/{run_id}`
- `GET /api/runs/{run_id}/stages`
- `GET /api/runs/{run_id}/artifacts`
- `GET /api/runs/{run_id}/skills`
- `GET /api/runs/{run_id}/evolution`
- `POST /api/runs/{run_id}/resume`
- `POST /api/runs/{run_id}/cancel`
- `POST /api/runs/{run_id}/evolution`
- `GET /api/batches`
- `GET /api/batches/{batch_id}`
- `POST /api/batches`
- `GET /api/skills/candidates`
- `GET /api/runs/{run_id}/artifacts/{path}`

### 9.2 当前研究任务

选择规则固定为：优先最新的 `running` 或 `queued` 运行；若没有，选择最近更新的运行；若没有任何运行，展示创建研究的空状态。

项目名称使用运行的 `direction`。状态、开始时间、更新时间、错误、恢复次数和阶段进度均取自 API。不能从显示文本推断运行成功。

### 9.3 八阶段生命周期

后端十二阶段通过显式映射归并为截图中的八个产品阶段：

1. 选题
2. 文献
3. 假设
4. 实验
5. 验证
6. 写作
7. 复盘
8. 进化

每个产品阶段的状态由其包含的后端阶段共同决定：任一失败则失败；任一运行中则运行中；全部完成才完成；其他情况为未开始。映射表写成纯函数并使用单元测试固定，不能在组件中散落字符串判断。

### 9.4 近期研究和趋势

近期研究表使用真实运行列表，展示题目、状态、阶段和更新时间。覆盖趋势只根据可验证的阶段完成比例或 API 明确提供的验证字段计算；没有历史样本时展示空图说明，不填充截图中的示例百分比。

### 9.5 审批与知识图谱

当前 API 没有审批列表、批准、拒绝和知识图谱查询端点。相应页面与卡片展示明确的能力状态，保留统一布局和导航，但不提供会改变业务结果的假操作。未来增加端点时，通过独立 feature adapter 接入，不改变 Dashboard 组件契约。

### 9.6 系统健康

系统状态条只展示 `/api/health` 返回的事实。无法从该接口确认的存储容量、GPU 数量和服务实例数显示为“未提供”，不沿用截图静态数值。

## 10. 核心交互

### 10.1 创建研究

“新建研究”打开右侧抽屉。表单包含科学问题、dry-run 选项和提交按钮。提交调用 `POST /api/runs`；成功后关闭抽屉、刷新运行列表、选中新运行并进入项目详情；失败时保留输入并显示服务端错误。

### 10.2 运行详情

点击当前任务、生命周期节点或运行表格行，进入运行详情抽屉或项目页。详情包含十二阶段、状态、错误、产物、验证结果、进化状态和恢复次数。

### 10.3 危险或不可逆操作

- 取消运行必须二次确认。
- 恢复运行和发起进化必须等待服务端成功后再刷新界面。
- 按钮在请求期间禁用并显示进行状态，防止重复提交。
- 409 等业务拒绝显示原始可理解信息，不改写为成功。

### 10.4 批量任务

项目空间提供批量任务入口。表单继续使用服务端可访问的 PDF 路径、题号范围和 dry-run 选项；创建成功后进入批量任务状态视图。路径错误和提取器错误显示在表单内。

### 10.5 下载产物

产物行展示文件名、类型、大小和校验信息。下载或预览使用服务端现有 artifact URL；不允许前端拼接越界路径。

## 11. 状态与错误处理

每个数据区必须有以下状态：

- 首次加载骨架。
- 后台刷新但保留旧内容。
- 空数据提示和明确下一步。
- 网络或服务错误，包含重试按钮。
- 操作成功反馈。
- 操作被业务门禁拒绝的警告。

全局错误边界只处理渲染异常；API 错误在所属功能区处理。错误消息不包含 API key、环境变量或本地绝对敏感路径。

## 12. 响应式与可访问性

- 1440 × 900 是像素级验收视口。
- 1280–1439 宽度保持两列关系，缩小卡片间距。
- 1024–1279 允许收起侧栏并压缩生命周期。
- 小于 1024 使用单列卡片和抽屉导航。
- 所有按钮有可见 focus 状态和可访问名称。
- 弹窗锁定焦点并支持 Escape 关闭；危险确认除外，必须显式选择。
- 表格在窄屏转为可横向滚动容器。
- 状态不能只依靠颜色表达，同时提供文字或图标。

## 13. 测试策略

### 13.1 单元测试

- 十二阶段到八阶段的映射。
- 当前运行选择规则。
- 状态、错误和产物类型格式化。
- API 请求参数和错误解码。

### 13.2 组件测试

- 创建研究成功和失败。
- 运行列表加载、空数据和错误。
- 恢复、取消和进化确认流程。
- 导航、主题和侧栏折叠。

### 13.3 后端回归

运行现有 `tests/unit/api/test_research_api.py`，确认静态资源、API 行为和安全边界未回归。

### 13.4 浏览器验收

使用真实浏览器在 1440 × 900 捕获参考状态，验证：

1. 首页布局与参考截图同构。
2. 侧栏导航全部可达。
3. 新建研究、选择运行、查看阶段和下载入口可操作。
4. 取消、恢复和进化的确认及错误状态正确。
5. 无 JavaScript 控制台错误。
6. 1280 宽度和移动降级布局可用。

视觉 QA 将参考图与本地截图在同视口并排比较，修复 P0、P1 和 P2 差异，最终报告写入项目根 `design-qa.md`。

## 15. 验收标准

完成必须同时满足：

1. 旧默认前端不再作为入口，新 React 应用成为唯一默认界面。
2. 1440 × 900 首页在结构、比例、颜色和密度上与参考图一致。
3. 现有健康、运行、阶段、产物、批量和技能 API 均有对应可用界面。
4. 主要按钮不存在静态空操作。
5. 后端缺少的审批与知识图谱能力被准确标识，不显示虚假数据。
6. 前端构建、单元测试、组件测试和 API 回归通过。
7. 浏览器主要交互通过，控制台无错误。
8. `design-qa.md` 的最终结果为 `passed`。
9. `Agent.md` 记录改动和验证；若 Git 元数据仍缺失，明确记录无法提交的既有阻断。

## 16. 回滚

实现期间保留旧文件的版本控制历史；新前端构建失败时不覆盖最后一个可运行的 `web/` 构建。由于当前工作副本缺少 `.git`，实施前必须先制作工作区内的只读文件清单和哈希记录，且每次覆盖仅针对新前端明确拥有的文件。

如果新前端在交付前未通过 API 回归或浏览器 QA，则不宣称完成，并在 `Problem.md` 记录阻断和恢复动作。
